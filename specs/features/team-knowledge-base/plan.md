# Plan: Team knowledge base skill

## Overview

The team skill is built from `src/team.md` (the team role text and rules) and
the same shared rules as the personal skill (`src/common.md`). The build from
`skill-build` joins them into `team-knowledge-base/SKILL.md`.

## Components Affected

- `src/team.md` — role text, the start message, and the added team rules.
- `src/frontmatter/team.yaml` — description and version.
- `team-knowledge-base/SKILL.md` — generated by `build.sh`.
- `tests/skills.test.sh` — gets the checks for the team rules (the file is listed in the plan of `personal-knowledge-base`).

## New Files

None. The files above exist already and are filled by this spec.

## Technical Approach

- The team rules add to the shared rules. They never repeat them. Behaviour that both skills share exists once, in `src/common.md`.
- Added rules: the person is responsible (author name and a reachable email, with a list of unusable address parts); folders are the team's own choice; fixing wrong documents with `disputed`; confidentiality; concurrent writes.
- Concurrent writes: after a rebase conflict the agent aborts the rebase, restores the remote version of the file, saves the person's version as `<file-name>-conflict.md`, marks it `disputed` with a reason, and tells the person. The repository never stays in a conflict state.
- Rule for deprecating a document of another team: only when the person says so clearly. Anyone may dispute.
- Size: the finished team skill stays below 16 KB.

## Cross-feature Dependencies

- `skill-build` (implemented).
- `personal-knowledge-base`: both skills share `src/common.md`. The team skill is planned after it, so the shared rules exist first.

## Risks

- The shared `AGENTS.md` is the same for everyone, so a team cannot set personal autonomy. This is deferred (see `todo.md`).
- The email list cannot catch every unusable address. The agent asks the person when unsure.
